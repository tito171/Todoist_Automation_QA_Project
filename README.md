# 📝 Todoist Automation QA Project

Учебный проект по атоматизации тестированию на примере реального веб-приложения Todoist методом «черного ящика». Включает в себя проверку отображения задач при установленных параметрах группировки и сортировки с применением архитектурных паттернов проектирования и гибридным подходом (UI + API).

---

## 🛠️ Стек технологий и инструменты

* **Язык программирвоания:** `Python 3.13+`
* **Тестовый фреймворк:** `pytest`
* **UI-взаимодействие:** `Selenium WebDriver`
* **API-взаимодействие:** `httpx`
* **Работа с данными:** `pytest-csv`, `json`
* **Управление конфигурацией:** `os`, `python-dotenv`
* **Автоматизация задач:** `taskipy`
* **Отчетность:** `Allure Report`

## 🧠 Архитектура проекта

### 1. Паттерн Page Object Model (POM) и декомпозиция

В проекте реализован классический паттерн **Page Object Model (POM)** в связке с **Component Object Model (COM)**. Страницы представляют собой высокоуровневые сущности, которые собираются из изолированных, повторно используемых компонентов (модальных окон, форм, панелей), что минимизирует дублирование локаторов и кода.

### 2. API предусловие

Для ускорения UI-тестов создание тестовых задач выполняется через API-запросы в `tests/conftest.py` с помощью библиотеки `httpx` перед запуском теста.

### 3. Тестирование сортировки и группировки задач (паттерны Strategy + Chain of Responsibility)

Реализованы тесты для проверки отображения списка задач при различных настройках сортировки и группировки.
Бизнес-логика проверки собранных с UI списков задач была вынесена в `tests/helpers.py` и завязана на поведенческих паттернах проектирования:

* **Стратегия (Strategy):** Разделяет алгоритмы проверки на независимые классы. Используются отдельные стратегии для валидации **группировки** и **сортировки** задач. Это позволяет динамически подменять правила валидации в зависимости от текущего набора исходных данных.
* **Цепочка обязанностей (Chain of Responsibility):** Применяется для реализации комплексной **каскадной сортировки** Todoist. Так как приложение имеет строгие вложенные правила ранжирования, цепочка проверяет условия последовательно:
  * *Звено 1:* Проверяет сортировку по основному критерию (например, по **Сроку**). Если сроки равны, передает управление дальше.
  * *Звено 2:* Проверяет сортировку по **Приоритету** (строго по убыванию). Если приоритеты равны, передает управление дальше.
  * *Звено 3:* Финально проверяет сортировку по **Дате создания** (строго по возрастанию).

### 4. Оптимизация скорости тестов

Для исключения временных затрат на чтение и парсинг файлов `.csv` с тестовыми данными во время выполнения UI-сценариев реализован механизм кэширования данных:

* Скрипт **`generate_test_data.py`** один раз вручную запускается перед тестированием, считывает таблицы через `python-csv` и автоматически генерирует чистый Python-файл **`test_data_store.py`**. Повторный запуск скрипта требуется только для актуализации данных.
* Тесты импортируют уже готовые структуры (списки словарей `LIST_OF_TASKS`, `ORDERING_TEST_DATA`), что исключает повторное чтение с диска и существенно ускоряет прогон.

### 5. Конфигурация и безопасность

Все настройки изолированы в файле `config`:

* Пути к тестовым данным (файлы csv с тестовыми данными).
* Глобальные переменные и базовые URL для разных окружений.
* Словари и карты соответствия для работы функций генератора тестовых данных и функций проверки отображения списка задач.
* **Безопасность:** Чувствительные данные (учетные записи для авторизации и API токен) вынесены в файл `.env` и не попадают в систему контроля версий.

## 🔄 Процесс работы и жизненный цикл теста (Workflow)

Каждый запуск теста представляет собой сквозной автоматизированный процесс, состоящий из пяти последовательных этапов:

### 1. Компиляция тестовых данных
* Перед стартом автоматизации запускается скрипт-кодогенератор `generate_test_data.py`.
* Он считывает эталонные параметры задач и тест-кейсы из CSV-матриц в папке `test_data/` и преобразует их в типизированные структуры Python внутри `test_data_store.py`. Это исключает затраты времени на парсинг файлов во время выполнения самих тестов.

### 2. Подготовка окружения
* Активируется pytest-фикстура в `conftest.py`, которая берет сгенерированные данные и через **SyncAPI (HTTPX)** пакетно создает пул задач на сервере. Это позволяет подготовить систему к тесту без медленных кликов на UI.
* Сразу после этого отправляется запрос к **REST API**, который собирает актуальную информацию о только что созданных задачах. Это необходимо, чтобы вытащить серверные `id` задач и точное время их создания, по которым в дальнейшем будет проверяться сортировка.

### 3. Выполнение UI-сценария
* Запускается браузер. Тест обращается к `LoginPage`, проходит авторизацию методом "черного ящика" с использованием учетных данных из `.env` и переходит на `InboxPage`.
* На странице списка задач применяются целевые комбинации сортировок и группировок.
* Тест взаимодействует со списком через `TaskListComponent` и собирает «сырые» текстовые и структурные данные отображаемых задач прямо с экрана.

### 4. Интеллектуальная валидация
* Данные, собранные с UI, передаются в модуль `helpers.py`.
* Чтобы тест оставался гибким и не превращался в нагромождение условий `if/else`, применяется паттерн **Стратегия**, который определяет правила валидации под выбранный тип группировки и сортировки.
* Внутри стратегии сортировки применяется паттерн **Цепочка обязанностей** для проверки соответствия взаимного порядка задач в списке правилам каскадной сортировки.

### 5. Очистка окружения
* Независимо от того, прошел тест или упал, срабатывает финальная часть фикстуры (Teardown).
* Одной командой через API удаляются все созданные для этого теста задачи. Окружение приложения возвращается в исходное чистое состояние, исключая появление «мусорных» данных при следующих запусках.

## ⚠️ Известные ограничения и статус отчетов

* **Примечание об актуальности отчета и видеозапись прогона:** Текущий HTML-отчет и видеозапись тестового прогона сохранены для демонстрации формата отчетности и работы тестов и отражают состояние проекта **до финального рефакторинга**. В них присутствуют устаревшие тесты проверки NLP-распознавания, которые были исключены из текущей версии репозитория, часть логики была переписана, структура проекта была переработана.
* **Блокировка прогонов со стороны приложения:** После обновления архитектуры проекта (внедрения Component Object Model) на стороне целевого веб-приложения усилились механизмы защиты от автоматизации. Поскольку тестирование проводилось методом черного ящика на реальном рабочем сервисе, выполнить прогон нового кода и пересобрать отчет не удалось.

## 🚀 Локальный запуск проекта

### 1. Предварительные требования

* **Python 3.13+**
* **Git**
* **Allure Commandline** (должен быть установлен в системе и добавлен в `PATH` для генерации отчетов)
* **Google Chrome** (актуальной версии для корректной работы Selenium WebDriver)

### 2. Клонирование репозитория

Откройте терминал, перейдите в папку, где хотите сохранить проект, и выполните:

```bash
git clone https://github.com/tito171/Todoist_Automation_QA_Project.git
cd Todoist_Automation_QA_Project
```

### 3. Создание и активация виртуального окружения

Чтобы изолировать зависимости проекта от глобальной системы выполните команды:

* **На Windows:**
  ```bash
  python -m venv .venv
  .venv\Scripts\activate
  ```
* **На macOS / Linux:**
  ```bash
  python3 -m venv .venv
  source .venv/bin/activate
  ```

### 3. Установка зависимостей

```bash
pip install -r requirements.txt
```

### 4. Настройка переменных окружения

В корне проекта создайте файл `.env` на основе шаблона `.env.example` и укажите ваши учетные данные для авторизации в Todoist:

```env
TODOIST_EMAIL=your_email_here@example.com
TODOIST_PASSWORD=your_password_here
TD_API_TOKEN=your_API_token_here
```

### 5. Запуск тестов и генерация отчета

*Для запуска полной сборки (очистка прошлых результатов, запуск тестов, сборка отчета и открытие его в браузере) выполните команду (команда настроена для **Windows** через `taskipy`):

  ```bash
  task report
  ```
*Для обычного прогона тестов без генерации отчета используйте стандартную команду:

  ```bash
  pytest
  ```

## ⚙️ Модификация тестовых данных (Кодогенерация)

Если вам необходимо изменить тестовые сценарии (обновить списки задач или правила группировки/сортировки):

1. Внесите изменения в соответствующие csv-файлы внутри папки `test_data/`.
2. Запустите скрипт генерации данных:
   ```bash
   python generate_test_data.py
   ```

Скрипт автоматически перепишет файл `test_data_store.py`, преобразовав таблицы в быстрые Python-структуры, и новые кейсы сразу подтянутся в тесты.
